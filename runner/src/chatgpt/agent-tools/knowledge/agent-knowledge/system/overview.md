# Automatio Agent Knowledge Overview

This directory contains the authoritative knowledge available to the Automatio AI workflow-building agent.

The agent is a **headless workflow-generation engine**. Its job is to understand a user's automation request and produce an execution-ready Automatio workflow as JSON.

The knowledge directory is divided into three areas:

```text
agent-knowledge/
├── nodes/
├── workflow/
└── system/
    └── overview.md
```

This file is the **system-level overview**.

The detailed node and workflow files are the authoritative source of truth for their respective areas.

---

# 1. Knowledge Areas

## `nodes/`

The `nodes/` directory contains the authoritative configuration and execution knowledge for individual Automatio node types.

Available node types:

* `trigger`
* `goto`
* `click`
* `fill`
* `select`
* `check`
* `uncheck`
* `press`
* `wait`
* `wait_for_element`
* `screenshot`
* `extract_text`
* `assert_text`
* `assert_value`
* `condition`
* `loop`
* `parallel`
* `call_api`
* `call_chatgpt`
* `telegram`
* `end`

There is also:

```text
nodes/index.md
```

which contains the supported node-type list.

Each node has its own knowledge file:

```text
nodes/<node_type>.md
```

For example:

```text
nodes/goto.md
nodes/click.md
nodes/fill.md
nodes/condition.md
nodes/telegram.md
```

These files contain the **actual configuration contract** for the node, including required fields, optional fields, allowed values, and node-specific rules.

### Important

Do **not** guess a node's configuration.

If the exact configuration of a node is not already known from the current context, use `call_system_files` to retrieve the corresponding node knowledge file.

For example, before generating an unfamiliar `telegram` node:

```text
call_system_files({
  "files": ["nodes/telegram.md"]
})
```

The retrieved file is authoritative.

---

# 2. Workflow Knowledge

The `workflow/` directory contains the rules for constructing the complete workflow.

Current workflow knowledge files:

```text
workflow/edges.md
workflow/output.md
workflow/rules.md
```

### `workflow/output.md`

Defines the shape of the workflow returned by the agent.

It explains the distinction between:

* the execution-ready workflow generated by the agent
* the Supabase representation created later by the application

The agent generates the former.

The agent must not generate Supabase persistence fields.

---

### `workflow/edges.md`

Defines how workflow nodes are connected.

Edges reference node `position` values.

The agent must use this file when it needs to reason about workflow connections, especially when dealing with control-flow nodes such as:

* `condition`
* `loop`
* `parallel`

---

### `workflow/rules.md`

Contains the hard invariants that every generated workflow must satisfy.

These include rules concerning:

* `trigger`
* `end`
* positions
* contiguous numbering
* node uniqueness
* valid node types
* valid configurations
* edges
* prohibited persistence fields

Before returning a workflow, the agent must ensure that the generated workflow satisfies these invariants.

If the exact rule is not already present in context, retrieve:

```text
workflow/rules.md
```

---

# 3. System Knowledge

The `system/` directory contains general agent-level instructions.

Currently the only system knowledge file is:

```text
system/overview.md
```

This file provides the high-level map of the knowledge directory.

It does **not** replace the detailed node or workflow files.

The detailed files remain authoritative for their respective subjects.

---

# 4. How Knowledge Retrieval Works

The agent has access to:

```text
call_system_files
```

Use it to retrieve knowledge from the `agent-knowledge` directory.

The agent should **retrieve only the files necessary for the current task**.

Do not blindly load the entire knowledge directory for every request.

### Example

If a user asks:

> Go to my website and click the Login button.

The relevant node knowledge may be:

```text
nodes/goto.md
nodes/click.md
```

If the agent already knows those exact contracts from the current context, it does not need to retrieve them again.

If it does not know the exact contract, retrieve them.

---

# 5. Knowledge Hierarchy

When generating a workflow, follow this hierarchy:

### 1. Workflow structure

Use:

```text
workflow/output.md
workflow/rules.md
workflow/edges.md
```

to determine how the workflow itself must be structured.

### 2. Node-specific behavior

Use:

```text
nodes/<type>.md
```

to determine how an individual node must be configured.

### 3. System overview

Use:

```text
system/overview.md
```

to understand where the relevant knowledge lives and how the knowledge directory is organized.

The overview should never be treated as a replacement for the detailed files.

---

# 6. Never Invent Node Knowledge

The list of supported nodes is finite.

The agent must never invent a node type.

If a requested action cannot be represented by the available node types, the agent must reason about whether the action can be accomplished using existing nodes rather than inventing a new one.

For example, an automation may combine:

```text
goto
fill
click
wait_for_element
extract_text
condition
telegram
end
```

to accomplish a larger task.

The user describes the **goal**.

The agent determines which supported nodes can execute that goal.

---

# 7. Browser Element Selectors

For browser interaction nodes such as:

```text
click
fill
select
check
uncheck
press
wait_for_element
extract_text
assert_text
assert_value
```

selectors must correspond to the actual page whenever the agent has access to page inspection through the available execution/inspection tools.

Do not invent selectors based solely on assumptions about a website.

If the agent needs page information to determine the correct selector, it should inspect the page using the appropriate available mechanism before constructing the workflow.

The workflow should contain the selector that is appropriate for the actual target element, not merely a guessed element name.

---

# 8. Variables

Several nodes can interact with values stored during workflow execution.

Examples include:

```text
extract_text
assert_text
assert_value
condition
loop
call_api
call_chatgpt
telegram
```

When a node uses a previously stored variable, follow the exact variable semantics defined in that node's knowledge file.

Do not invent variable syntax or configuration fields.

---

# 9. Control Flow

Some nodes are not simple sequential browser actions.

The main control-flow nodes are:

```text
condition
loop
parallel
```

These can change the workflow's execution relationships.

When generating workflows containing these nodes, retrieve their node-specific knowledge if necessary and consult:

```text
workflow/edges.md
```

to construct the appropriate edges.

Do not assume that every workflow is simply a linear chain.

---

# 10. Integrations and AI

Automatio currently includes nodes for external/API/AI actions:

```text
call_api
call_chatgpt
telegram
```

These are still ordinary Automatio workflow nodes.

Their exact configuration must come from:

```text
nodes/call_api.md
nodes/call_chatgpt.md
nodes/telegram.md
```

Do not invent integration-specific fields.

---

# 11. Trigger and End

Every valid workflow has a beginning and an end.

The beginning is represented by:

```text
trigger
```

The successful termination of the workflow is represented by:

```text
end
```

Their exact structural requirements are defined in:

```text
nodes/trigger.md
nodes/end.md
workflow/rules.md
```

Those rules are mandatory.

---

# 12. Supabase Is Not the Agent's Output Format

The agent generates an **execution-ready workflow**, not database rows.

Do not output fields belonging to the application's persistence layer such as:

```text
id
automation_id
created_at
updated_at
position_x
position_y
```

The application is responsible for converting an accepted generated workflow into its persistence representation.

The authoritative output contract is:

```text
workflow/output.md
```

---

# 13. Final Validation

Before returning a generated workflow, the agent should verify:

1. Only supported node types are used.
2. Every node has a valid configuration.
3. No unknown configuration keys were invented.
4. Workflow positions are valid.
5. `trigger` requirements are satisfied.
6. `end` requirements are satisfied.
7. Edges reference existing nodes.
8. Control-flow relationships are valid.
9. No Supabase persistence fields are present.
10. The final JSON follows the workflow output contract.

When necessary, retrieve:

```text
workflow/rules.md
workflow/output.md
workflow/edges.md
```

before performing this validation.

---

# Core Principle

**The overview tells you where knowledge lives. The detailed knowledge files tell you what is valid.**

Do not duplicate or infer detailed schemas when the authoritative file can be retrieved.

When in doubt about a node or workflow rule:

```text
call_system_files
```

and retrieve the relevant authoritative knowledge file.
